上一篇把[一车一授权、nonce 和 AVB 防回滚](/post/vehicle-authorization-nonce-avb.html)放在一起看，主要在回答：这份软件和授权材料，设备现在还认不认？

但后面还有一段没接上。Bootloader 验完镜像，留下一份结果，系统继续启动。到了某个服务准备使用设备密钥的时候，它凭什么知道前面的验证结果？即便拿到了，又该怎么决定这次请求能不能执行？

我想把这一段补上。否则前面是 RSA、Hash、rollback index，后面突然冒出一个 `auth_role`，中间一根箭头，仿佛权限自己就算好了。图画得很顺，读代码的时候还是会卡住。

这篇沿用公开的 AVB、Linux 和 TF-A 资料，把“验证了什么”和“允许做什么”连起来。文中的 `auth_role` 只是业务侧授权结果的统称，不是 AVB 的标准字段，也不对应某款产品的角色编号。

## 公钥也在镜像里，为什么不能一起换掉

先回到一个很基础的问题。镜像的认证元数据里有公钥、有摘要，还有签名。攻击者自己生成一对密钥，把镜像改掉、摘要重算、签名也重做一遍，数学上完全可以验过。

所以单看 `verify_signature()` 返回成功，还回答不了“这是谁批准的软件”。它只说明签名和参与验证的那把公钥能对上。

AOSP 对这个边界写得很直接：`avb_vbmeta_image_verify()` 即使返回成功，调用者仍要确认内嵌公钥是否受信任，并检查 rollback index。它是验证 vbmeta 数据的底层函数，更高层的分区验证入口是 `avb_slot_verify()`。[固定版本的接口说明](https://android.googlesource.com/platform/external/avb/+/761178607206f4cb2af79ed9eec52d8cbd814adb/libavb/avb_vbmeta_image.h#246)

这就把问题往前推了一步：设备允许哪把公钥给这个分区签名？

在 AVB 的链式分区设计里，已经受信任的上级元数据可以指定子分区的验证公钥。这样，不同分区可以交给不同密钥管理。子分区不能靠自己携带一把新公钥，就宣布自己可信。[AVB 的链式分区说明](https://android.googlesource.com/platform/external/avb/+/761178607206f4cb2af79ed9eec52d8cbd814adb/README.md#the-vbmeta-struct)

上级元数据凭什么可信，还要继续往前追，直到硬件保护的信任根。验证代码本身也在这条关系里。如果它能被任意替换，后面的检查再细，攻击者也可以直接跳过。这里追的是“谁认证谁”，具体有几级 Bootloader、每一级叫什么，要看平台，不能拿某张启动图当成所有 ARM 设备的固定流程。[Android Verified Boot 概述](https://source.android.com/docs/security/features/verifiedboot)

## 开机时没把整个分区读完，后面怎么办

如果启动时要读入一份完整镜像，可以在使用前核对它的摘要。但 `system` 这类大分区里的内容，很多要等系统运行以后才会读到。

这时就能接上 dm-verity：启动验证链先认证哈希树的根摘要，Linux 随后通过 dm-verity 读取受保护的数据块，按需校验它们与这个根是否一致。根摘要自身必须有可信来源，否则攻击者把数据和整棵树一起换掉，还是能相互对应。[Linux dm-verity 文档](https://docs.kernel.org/admin-guide/device-mapper/verity.html)

于是，启动阶段交下去的东西不只有“验证通过”四个字，还可能包括受认证的根摘要，以及用于建立 verity 映射的设备、块大小等参数。使用了哪个分区、映射覆盖多大范围，也会影响最终检查到什么。

这里容易把“运行时校验”听成“运行时都安全”。dm-verity 检查的是经过该映射读取的数据块，挡不住已经受信任的代码本身存在漏洞，也不会顺手检查所有可写数据和内存。内核如果已经被攻陷，单靠它继续执行的检查，更不能提供原先的保证。

错误处理同样要看配置。Linux 文档列出了 `ignore_corruption`：记录损坏，但允许读取继续。其他配置可以让错误导致 I/O 失败、重启或 panic。排查时只确认“启用了 dm-verity”还不够，得把发现不一致之后的动作也读完。

## 一个 GREEN，还装不下全部信息

验证结果到了启动流程，通常会被整理成某种 boot state。颜色很方便，但我更想知道颜色后面保留了哪些条件。

以 Android 的公开定义为例，传给系统的 `green` 对应锁定且未使用用户自设信任根的启动状态；`yellow` 对应锁定、使用用户自设信任根；`orange` 对应解锁。Android 12 及以后还可以通过 bootconfig 传递这些信息，不必一律画成 kernel cmdline。[Android 启动状态传递](https://source.android.com/docs/security/features/verifiedboot/boot-flow#communicate-verified-boot-state-to-android)

同一份文档里的 RED 警告又分 dm-verity 损坏和找不到有效系统等情况，对应动作也有区别。换到其他平台，还要分别查清颜色的产生条件和对应动作，同名状态未必采用同一套策略。

允许解锁设备运行自定义系统，是启动策略做出的选择。上层服务是否允许在这种环境里使用某项能力，是后续的另一个决定。一个状态可能允许系统启动，却不满足某项密钥操作的要求。

Android 的密钥证明提供了一个公开例子：`RootOfTrust` 里分别有 `deviceLocked`、`verifiedBootState`、`verifiedBootKey`（公钥摘要），以及较新版本里的 `verifiedBootHash`。这些字段让接收方有条件区分启动环境；它们不会替所有业务直接算出一个“允许”。如果拿证明给远端判断，还要验证证明链、挑战新鲜性及相关字段，不能只摘出一个颜色看。[Key attestation 的 RootOfTrust 字段](https://source.android.com/docs/security/features/keystore/attestation#rootoftrust-fields)

前面讲过的 nonce、rollback index、RPMB 也各有作用。nonce 参与授权状态判断，rollback index 限制可接受的软件安全代际，RPMB 一类机制保护跨重启保存的状态。不能因为这些信息最终都供安全策略使用，就把它们压成同一个“安全等级”。

## 写进共享内存，TEE 就能信了吗

启动阶段知道结果，不代表后来的每个使用者都自然知道。

Bootloader 可以保存本次启动状态，也可以把部分信息交给安全侧，再把用于展示或普通系统策略的副本传给 Linux。每条路径都要单独回答：谁写的，什么时候写的，写完以后谁还能改？

假设共享内存里有个 `verified = true`。这个值本身没有证明力。如果普通世界能够在检查前把它改成 true，安全侧读到的也只是一次普通写入。换成一个更长的 magic，问题仍在。

SMC 也不会自动补上这层保证。TF-A 的 BL31 在 EL3 处理运行时服务，SMC 的 Function ID 用来分派请求；服务仍需要检查调用来源、参数和调用条件。进入了高权限处理函数，并不表示传进来的每个字段都是真的。[TF-A 运行时服务说明，固定提交](https://github.com/TrustedFirmware-A/trusted-firmware-a/blob/1d5aa939bc8d3d892e2ed9945fa50e36a1a924cc/docs/design/firmware-design.rst#L889)

拿“记录本次启动结果”来说，我会接着查几个具体地方：

- 哪个阶段有权写入，普通系统起来以后还能不能覆盖。
- 收到的是本次启动结果，还是上一轮留下的状态；缺失、重复和非法值怎么处理。
- 使用共享缓冲区时，检查过的数据会不会在使用前又被改掉。

比如可信阶段完成初始化后关闭写入口，是一种可能的设计，但“只允许写一次”本身也不够：第一次写必须来自被允许的阶段。否则只是替第一个抢到接口的人保存了结果。

对普通系统可写的共享数据，复制到受保护内存后再校验、使用同一份副本，可以减少检查与使用之间的数据变化；它仍然不能证明发送者的说法属实。缓冲区稳定性和数据来源可信，是两件都要处理的事。

这也解释了为什么我不会把 cmdline 里的状态直接当成 TEE 的授权凭据。启动参数可以承担正常的状态传递，但如果威胁模型包含普通系统被攻陷，安全侧就需要自己可信地获得和保存依据。让上层把它读出来、再原样送回去，不能凭空恢复信任。

KeyMint 的公开接口也把这件事单独列了出来：Root of Trust 在启动期间提供给安全环境，优选由 Bootloader 提供，具体传递机制由实现决定。这和把启动颜色输出给 Android，是两个需要分别核对的接口。[KeyMint 的 Root of Trust Binding](https://android.googlesource.com/platform/hardware/interfaces/+/d0ed43bb7eeb8c2cdc23d23d0d926e083322b7f3/security/keymint/aidl/android/hardware/security/keymint/IKeyMintDevice.aidl#189)

## auth_role 到底在合并什么

到这一步，才轮到业务授权。

假设一项能力要求：启动环境满足策略、本机的软件授权有效、这次调用者也有使用资格。前两项成立，不代表第三项可以省略。一份合法系统里，也有权限不同的进程。

`auth_role` 可以用来表示整理后的结果，但结果至少要说清适用对象和操作。允许读取诊断信息、允许安装经过认证的恢复包、允许使用设备私钥，这几项权限未必能排成从小到大的一条线。

这会影响一个很常见的写法：

```c
final_role = max(boot_role, device_role, service_role);
```

这里只是一个合并方式的示意。如果角色数值越大，允许的操作集合就越小，而且所有角色都按这个顺序严格包含，那么取最大值可以表达“按最严格条件处理”。这个前提得写在定义里，并随着角色变动一起检查。

但考虑两个自己构造的权限集合：

```text
角色 A：{读取诊断信息, 安装恢复包}
角色 B：{读取诊断信息, 使用业务密钥}
```

A 和 B 谁更严格？A 少了密钥权限，B 少了恢复权限，单看枚举数字比不出来。如果它们代表必须同时满足的两项限制，那么合并以后只剩“读取诊断信息”。取 A 或取 B，都会额外放进一项权限。

因此我更倾向先写清楚每个操作的判断条件，再决定是否需要压成角色枚举。取权限集合的交集，也只有在各输入确实代表对同一主体、同一上下文的限制时才成立；用于授予额外权限的凭据，合并规则又会不同。

没初始化、解析失败、遇到未知枚举时，也得有明确结果。对依赖这份证据的敏感操作，可以先拒绝；如果需要保留恢复能力，就给恢复路径单独定义允许范围和认证条件。恢复不能简单理解成把普通业务检查全部关掉。

## 最后那次拒绝，应该发生在哪里

假设现在已经算出了正确的授权结果，页面也把“使用设备密钥”的按钮置灰了。这能避免用户误操作，但调用者还可能绕过页面，直接调用后面的接口。

如果密钥操作在 TA 里，真正掌握密钥的可信代码就要执行相应检查。它应根据可信获得的启动证据、有效授权和当前请求来决定，而不是直接接收上层传入的 `allowed=true`。调用者身份本身也需要在威胁模型里说明：在普通内核已被攻陷的前提下，上层自报的 UID 或进程名不足以建立身份。

这不是要求所有业务一股脑搬进 TEE，而是要看攻击者能绕过哪些层。只在 HAL 包装函数检查、底下却留着可直接调用的入口，和在最终操作处检查，约束能力不同。同样，检查通过以后，操作对象、输入缓冲区或授权状态如果还能变化，也要避免实际执行的已经不是刚才批准的那次请求。

启动证据记录的是本次开机时的状态。授权撤销、维护模式切换却可能发生在运行中，所以缓存角色是否还有效，要看它依赖的哪些条件已经变化。执行敏感操作时，需要重新确认这些会变化的条件。

所以我现在看这类代码，会先找到最终使用密钥、写状态或放行安装的地方，再反过来找它的判断依据。这样比较容易发现一条检查到底只影响了日志，还是确实挡住了后面的操作。

## 用几个反例检查这条线有没有接上

把上面的关系画完以后，可以先做纸面推演。下面列的是预期检查点，不是已经跑过的攻击实验：

| 改了什么 | 应该继续追哪一步 |
| --- | --- |
| 改镜像，同时重算摘要并用自己的密钥签名 | 公钥是否被可信上级授权 |
| 换回一份签名正确的旧镜像 | 它的 index 是否低于已保存下限；“旧”本身还不够 |
| 受保护分区的数据块被改了 | 读取是否经过 verity，错误最终如何处理 |
| 把普通世界展示的状态改成“通过” | 可信侧是否错误地接受了这个副本 |
| 启动证据缺失或角色解析失败 | 是否拒绝依赖它的操作，恢复权限是否独立受限 |
| 绕过 UI，直接请求使用密钥 | 最终接口是否仍执行授权检查 |

对我来说，接下来读源码最值得多停一会儿的，反倒是验签返回之后的那几十行：结果赋给了谁，失败分支有没有留下可被误用的值，传下去以后谁还会检查。

本文依据公开源码和文档整理，AVB 源码固定在 `761178607206f4cb2af79ed9eec52d8cbd814adb`；没有做设备上的启动故障注入或业务授权实验。
