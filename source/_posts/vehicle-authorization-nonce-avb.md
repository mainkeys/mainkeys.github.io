假设有两台同型号的车机，硬件兼容，也信任同一套厂商签名。把甲设备上的软件和授权文件复制到乙设备，镜像签名依然可能是对的。

这时安全启动能回答“软件有没有被改、签名者是否受信任”，但业务还会追问：乙设备获得过运行这套软件的授权吗？这份材料是不是从另一台设备搬来的？它以前有效，现在还有效吗？

一车一授权要处理的就是这些约束：把设备身份和软件内容关联起来，再跟踪授权状态的变化。我想弄清的是，这里面的 nonce 和防回滚到底各管哪一段。旧授权被拒绝，AVB 也拒绝旧镜像，看上去都有个“旧”字，判断依据却不同。

下面用一个简化的设备授权协议推演升级过程。设备名、摘要和 nonce 都是示例，`accepted`、`pending` 是为说明状态而取的名字，不是某款产品的接口定义。AVB 部分独立对照 AOSP 固定提交 [`761178607206`](https://android.googlesource.com/platform/external/avb/+/761178607206f4cb2af79ed9eec52d8cbd814adb/)，按锁定设备、正常强制验证的路径讨论。

## 一份授权至少要和什么绑在一起

先考虑一份由授权服务签发的材料，里面覆盖设备身份、软件摘要和授权状态值。把签名内容抽象成这样：

```text
签名覆盖的内容：
  协议版本与用途
  设备身份
  被批准的软件摘要
  本轮授权状态值
  其他必要的策略约束
```

设备身份得在签名覆盖的内容里。只是把它放在文件旁边，替换身份值可能根本不会破坏签名。协议还要规定字段编码、长度和用途，验签时使用设备信任的密钥或证书策略；文件自带的公钥能验过签名，并不足以让设备信任它。

设备收到材料后，还要拿本机身份、准备运行的软件和当前可信状态逐项对照。验签通过只是其中一步。

“一车”具体指哪个身份，也要说清楚。绑定控制器的硬件身份之后，它和整车 VIN 的关系仍要另外建立；换板、维修、重新配对时，这个关联也要可靠地更新。身份值本身可以公开，关键是设备用来对照的本机身份从哪里来。如果完全由上层进程提供，就很难靠它判断材料有没有被搬到另一台设备。

## 授权的软件，和真正启动的镜像

再看软件这一边。授权文件可能批准的是一份软件清单，启动时却要加载一组具体镜像，这两者之间还缺一段对应关系。

授权绑定的摘要要对应当前使用的软件清单，清单中的各项特征再对应实际被验证和加载的镜像。只对版本号字符串，通常还不够。

AVB 可以为第二步提供已经认证的镜像描述信息。签名的 vbmeta 包含 hash、hashtree 或 chain partition 等描述符；hash 描述符对应镜像内容，哈希树还可以把完整性检查延续到后续数据块读取。业务授权选用哪个摘要，取决于协议约定的分区集合和计算方法。[AVB 数据结构说明](https://android.googlesource.com/platform/external/avb/+/761178607206f4cb2af79ed9eec52d8cbd814adb/README.md#the-vbmeta-struct)

例如 AVB 的 vbmeta digest 覆盖主 vbmeta 和所关联的链式 vbmeta，有明确的计算范围。把几个镜像 Hash 拼起来再算一次，得到的是另一个东西。用它关联授权时，签发端和设备端要按同一定义计算，实际镜像则继续由验证链约束。[vbmeta digest 的计算范围](https://android.googlesource.com/platform/external/avb/+/761178607206f4cb2af79ed9eec52d8cbd814adb/README.md#the-vbmeta-digest)

查调用链时，我还会往后找谁使用了检查结果。验证失败以后，如果只是打印日志，后面仍然照常启动，这次检查就没有约束住启动行为。结果可以通过共享内存或启动参数传递，但最终仍要有人据此决定继续、拒绝还是进入恢复流程。

## nonce 到底在哪一步失效

nonce 常见于挑战应答：验证方生成不可预测的随机值，对方把它和响应内容一起签名。验证方检查响应是否匹配当前挑战，并管理挑战的有效期和使用状态。这能判断响应的新鲜性；随机值本身没有软件版本的先后含义。[RFC 9334 对 nonce 新鲜性的说明](https://www.rfc-editor.org/rfc/rfc9334.html#section-10.2)

设备离线启动时，往往还要允许同一份已激活授权重复使用。如果每次正常开机都消耗掉它，下一次开机就得重新申请。为了讨论这种情况，给每个目标槽关联两项可信状态值：

- `accepted`：当前已经确认的启动授权状态值。
- `pending`：为下一轮升级准备的状态值。

假设这次从 A 升到 B，只看目标槽 B。它原来的状态是 `(accepted=N0, pending=N1)`，服务为新软件签发的授权带着 N1。第一次从 B 启动时，在允许试启动的流程中检查 N1 是否匹配 pending。等这次升级满足成功条件，再提交为 `(accepted=N1, pending=N2)`。

```text
准备升级：  accepted=N0  pending=N1
新授权：    绑定本机、新软件摘要、N1
首次启动：  N1 匹配 pending
成功提交：  accepted=N1  pending=N2
后续启动：  同一份授权的 N1 匹配 accepted
```

授权里的 N1 一直没变。首次启动时，它匹配的是待确认升级；提交后，它匹配的是当前已确认状态。这里虽然沿用 nonce 这个名字，实际讨论的是一个有生命周期的授权状态值。离线设备还要靠同一份授权正常开机，并不适用在线挑战“一次响应后作废”的全部规则。

B 只是这次的目标槽。下一次可能从 B 升到 A，产品也可能允许原地升级。申请 nonce、写授权、装镜像和提交状态时，都得确认这次操作的目标。“当前槽”“对端槽”与授权文件的“主副本”“备副本”各自指什么，也要分别核对，单看一个“备”字很容易找错对象。

获取 pending 时，已有有效值就按协议返回它。假如申请已经带着 N1 发出去，另一次“获取”却把它换成 N2，服务返回的授权在本机就对不上了。不过，首次初始化或原状态无效时，这个接口可能负责生成并保存新值。所以看 getter 时还要查它在哪些条件下会写状态。

恢复流程也可能准备新的待申请值，同版本维修可能同步授权及其对应状态。因此，查状态变化还要把这些入口算进去。刷新、同步和成功提交的前提各不相同，复制完成之后，源授权是否有效、软件是否相同、目标有没有选对，仍是要检查的条件。

## 拒绝旧授权，还不能直接推出版本防回滚

目标槽 B 只接受 N1、N2 时，带 N0 的旧授权就会失败。只要验证方的可信状态没有退回去，这个判断就能限制旧授权材料的重放。

但如果授权服务把一个较旧的软件摘要和当前 N2 一起签发，本机的 nonce 检查仍可能通过。它只能看出“这份材料属于当前允许的授权状态”，看不出这个摘要对应的软件是否修复了某个漏洞。

另一种情况更直接：旧授权、旧镜像、旧的 `(accepted, pending)` 一起恢复，相等判断又会成立。即便状态文件带有正确 MAC，旧文件也可能有一个正确的旧 MAC。完整性校验并不自动证明这是最新状态。

这两个例子里，nonce 相等检查都正常工作，旧软件却仍有机会被接受。防回滚方案还需要管住签发策略、可信状态的历史，以及验证代码本身的版本；`nonce == stored_nonce` 只覆盖了其中一项判断。

## AVB 比较的是一条有方向的门槛

AVB 的 rollback index 是一个有序数值。镜像携带的值在经过认证的 vbmeta 头中；设备通过平台提供的可信持久状态保存下限。对使用到的每个位置 n，核心条件是：

```text
image_rollback_index[n] >= stored_rollback_index[n]
```

例如设备门槛为 7，携带 6 的镜像即使签名合法，也会在防回滚检查中失败；携带 7 可以通过这一项检查，也允许反复启动，正常开机不会消耗这个值。

这个数值表达的是发布策略定义的安全代际，不一定等于界面上的软件版本号。两个版本使用相同 index 时，这项比较无法区分它们；只要都满足下限，它就不会阻止两者切换。要淘汰某个旧版本，发布策略就得给新旧软件划分相应代际。[AVB 的 rollback protection 定义](https://android.googlesource.com/platform/external/avb/+/761178607206f4cb2af79ed9eec52d8cbd814adb/README.md#rollback-protection)

还要区分值与位置：`rollback_index` 是要比较的数，`rollback_index_location` 表示使用哪一个持久化计数位置。后者不是系统 A/B 槽号，也不是 RPMB 里的字节偏移。

在这个版本的常规 vbmeta 路径中，主 vbmeta 使用其头里的位置；链式 vbmeta 使用父级 chain descriptor 指定的位置和公钥约束。位置到实际安全存储的映射由平台处理，A/B 槽的切换不会因此自动获得两套可任意倒退的独立下限。[位置选择和索引检查源码](https://android.googlesource.com/platform/external/avb/+/761178607206f4cb2af79ed9eec52d8cbd814adb/libavb/avb_slot_verify.c#854)

多个位置要分别比较。假设设备下限为 `[7, 13]`，新软件对应值为 `[8, 12]`，第一项通过，第二项仍然失败。主系统从 7 提到 8，并没有补偿另一项退到 12；要看的是整个镜像集合是否满足要求。

把这两种判断并排放一下：

| 比较项 | 本文的授权状态模型 | AVB 版本门槛 |
| --- | --- | --- |
| 核心判断 | 状态值是否匹配 | 版本值是否低于下限 |
| 是否表达版本先后 | 随机值自身不表达 | 由发布策略赋予顺序 |
| 何时变化 | 本例在成功提交时轮换，恢复另定规则 | 满足成功策略后提高 |
| 当前软件重复启动 | 可匹配已确认状态 | 相等仍可通过 |
| 仍需另行约束 | 新授权能否批准旧软件 | 逐设备的业务授权 |

## 沿源码看，比较和写入分在哪里

`avb_slot_verify()` 会加载、验证 vbmeta，检查密钥是否受信任，再通过 `AvbOps` 读取对应的持久化 index。固定版本的 `load_and_verify_vbmeta()` 里可以找到 `read_rollback_index()`，随后用小于比较产生 `AVB_SLOT_VERIFY_RESULT_ERROR_ROLLBACK_INDEX`。

把这部分抽成伪代码，是下面这个意思，省略了 I/O 错误、内存错误和解锁设备的特殊处理：

```text
stored = platform.read_rollback_index(location)
if authenticated_vbmeta.rollback_index < stored:
    return ERROR_ROLLBACK_INDEX
```

验签通过还要经过信任判断。常规主 vbmeta 路径调用 `validate_vbmeta_public_key()`，由平台决定这把公钥是否可接受；知道文件能用某把公钥验过，并不表示设备应该信任这把公钥。[验证和密钥检查实现](https://android.googlesource.com/platform/external/avb/+/761178607206f4cb2af79ed9eec52d8cbd814adb/libavb/avb_slot_verify.c#789)

继续往后看，验证得到的各位置 index 被放进了 `AvbSlotVerifyData.rollback_indexes`。`avb_slot_verify()` 到这里还没有把它们写回设备，接口注释把持久化更新留给了调用者。[`avb_slot_verify()` 的接口约定](https://android.googlesource.com/platform/external/avb/+/761178607206f4cb2af79ed9eec52d8cbd814adb/libavb/avb_slot_verify.h#215)

`AvbOps` 提供 `read_rollback_index()`、`write_rollback_index()` 等回调，存储、访问控制和失败处理由平台落实，RPMB 布局也没有统一规定。调用者拿到验证错误后，要让它真正影响启动选择。[平台回调约定](https://android.googlesource.com/platform/external/avb/+/761178607206f4cb2af79ed9eec52d8cbd814adb/libavb/avb_ops.h)

前面那套业务授权流程需要单独实现。基础 AVB 没有自动提供它，不过平台可以扩展公钥信任策略，或结合其他授权机制来做设备绑定。

## A/B 的失败回退，为什么怕过早提交

假设 A 槽是旧系统，index=7；B 槽刚安装新系统，index=8；设备当前下限是 7。

第一次尝试 B 时，`8 >= 7`，防回滚检查通过。可这只能说明它符合安全版本门槛，不能证明系统启动后功能正常。如果还没确认 B 成功就把下限写成 8，而 B 随后启动失败，再选回 A 就会遇到 `7 < 8`。

AOSP 对 A/B 的建议是：从标记为 `SUCCESSFUL` 的槽更新防回滚元数据，避免失败升级提前淘汰旧槽。固定版本 README 给出了一种实现方式：系统先确认成功，之后 bootloader 再次启动这个成功槽时推进持久化 index。[A/B 启动要求](https://source.android.com/docs/security/features/verifiedboot/boot-flow#flow-for-ab-devices)、[持久化 index 更新时机](https://android.googlesource.com/platform/external/avb/+/761178607206f4cb2af79ed9eec52d8cbd814adb/README.md#updating-stored-rollback-indexes)

新版本还没确认时，保留旧槽有助于失败恢复。门槛正式提高后，低于门槛的旧槽就会被淘汰，后续恢复也只能选择满足新门槛的镜像。旧槽能保留多久，和这个提交点有关。

业务激活成功和 A/B 的 `SUCCESSFUL` 标记也未必是同一个事件。前者可能还包含授权验证、服务健康检查等产品条件。接入时要逐项确定：哪段代码确认这种成功，它能推动哪项可信状态，恢复路径又适用什么门槛。

## 把几项提交放回同一次升级里

B 槽装好新文件以后，后面还有几项状态要处理：授权从 pending 转成 accepted，A/B 元数据确认成功，AVB 下限可能从 7 变成 8。

先看一个没有额外防重复约束的反例：提交接口不带期望状态，只要调用就执行“把 pending 复制给 accepted，再生成下一轮 pending”。第一次提交把 `(N0, N1)` 改成 `(N1, N2)`，如果返回丢了，上层重试一次，就可能继续改成 `(N2, N3)`；授权文件却仍然带着 N1。

实际流程可能用任务标记、恢复记录或调用门禁防止重复推进，这要沿具体入口去查。尤其要留意状态记录的时间：重启后重新验证的结果，与本次开机时留下的快照，含义不同。启动时记录了“匹配 pending”，运行中提交完成了，旧记录未必跟着更新。再拿它决定是否提交，就可能重复处理同一轮升级。

调用权限之外，还要判断当前是否需要改状态。例如让请求绑定具体事务和预期旧状态：同一事务已经提交，就返回既有结果；状态不符合预期，就拒绝继续推进；检查和更新在可信侧串行执行。后面的模型按这种约束检查重复调用，实际工程的其他入口仍要分别核对。

再看掉电。假设 accepted 连同完整性信息已经有效落盘，pending 还没换新，会留下 `(N1, N1)`。匹配规则如果先检查 accepted，再检查 pending，新授权就会先命中 accepted，仍然可能启动。这里假设两项状态都完整有效；如果某项状态或校验信息只写了一半，就要进入相应的有效性检查和恢复流程。

即使每次写操作都是原子的，nonce、slot-success 和 rollback floor 三项之间仍可能只完成了一部分。一种设计是用有完整性保护且抗回滚的事务记录，保存目标槽、已验证的软件身份、预期旧状态和提交阶段，再按存储能力定义各个掉电点的恢复动作。重试哪些步骤、跳过哪些步骤，都要有对应依据。

index 更新也有它的特点：把下限从 7 提到 8 后，再写同一个 8，在数值上不会像 nonce 轮换那样变成下一轮状态；但更新多个位置时仍可能部分成功。已经提高的安全门槛通常不能靠写回较小值补救，所以恢复镜像、剩余槽及其他位置要能与已提交部分相容。

我还会确认返回码的具体含义。接口返回成功，可能确实改了状态，也可能发现这次不适用、无须重复执行。回到旧槽以后，残留的升级任务可能只需要结束和清理；任务处理完，并不表示新状态已经提交。

## 都放进 RPMB，也不会变成同一套状态

RPMB 可以为可信存储提供经过认证且抵抗重放的读写机制。它的写计数器服务于存储协议，其他合法写操作也会改变这个计数。因此，它与业务 nonce、AVB 安全代际各有含义，存储写了多少次，并不对应软件升级了多少代。

上层可信代码允许写入什么，也会影响结果。攻击者重放旧的原始存储请求，可以由存储协议拒绝；获得写权限的服务重新写入旧业务状态，却可能是一笔新发起、认证有效的写操作。后者需要业务状态规则来约束。

OP-TEE 的公开文档也分别说明了存储完整性保护和防回滚配置。对象保存在 TEE 里之后，历史是否受保护仍要看具体配置。[OP-TEE 可信存储说明](https://optee.readthedocs.io/en/4.10.0/architecture/secure_storage.html#globalplatform-trusted-storage-requirement)

数据和反码副本用于检查某些损坏，完整性标签用于检查未经授权的修改，抗回滚状态约束接受哪一段历史。除了存储这些数据，还要检查哪些可信代码和恢复入口有权更新它们。

## 用一个状态模型把区别跑出来

我把上面的比较写成了一个只用 Python 标准库的小模型，使用合成设备名、摘要和符号 nonce。脚本先建立第一份授权，再用下一轮状态观察替换和重放。签名与镜像密码学校验假设已经由前置步骤完成，脚本只检查授权状态和版本门槛，不包含 RPMB、TA 或真实的 `libavb` 调用。

脚本额外保存了候选授权和完整的已确认令牌，用它们绑定软件身份、识别重复提交。正文状态图只画 nonce 值，脚本里的 `accepted` 则包含设备、摘要和 nonce。这是为了推演加入的约束，与具体固件的存储布局无关；脚本也没有模拟掉电恢复。

代码：[authorization-model.py](/post/vehicle-authorization-nonce-avb/authorization-model.py)。保存后运行：

```sh
python authorization-model.py
```

脚本需要 Python 3.10 或更新版本。9 月 19 日的本地运行退出码为 0，13 个场景均符合预期，最后一行输出为：

```text
PASS: 13 model scenarios; no hardware, CA/TA, RPMB or AVB test performed.
```

PASS 表示模型行为符合场景预期。其中第 9 项恢复旧快照、第 12 项提前提高门槛，演示的恰好是重放风险和回退受阻。这 13 项是状态推演的检查结果，没有验证产品安全性。

模型先检查设备、摘要和 nonce 是否匹配，再观察 pending 提交后同一份授权继续启动、重复提交不再次轮换的行为。只重放旧授权时检查失败，连旧状态一起恢复后，匹配又通过了；如果 AVB 下限仍保持较高值，旧镜像还会受到独立的版本检查。其余场景检查了 index 等于下限时重复启动，以及过早提高下限对 A/B 失败回退的影响。

第 13 项是重新签发的情况：服务用当前 pending 为旧软件签发一份新授权。授权这一侧可以接受它，独立的 AVB 比较仍然因为 `7 < 8` 拒绝旧镜像。模型把两项条件分开观察；实际启动流程要先通过全部必需检查，才有成功状态可提交。

回到升级排查，我会把授权文件、实际启动槽、可信 nonce 状态和已存 index 放在一起看：是授权状态没匹配，还是软件低于安全门槛？失败前哪些状态已经提交？这些信息比单独一条“授权失败”或“防回滚失败”日志更容易定位问题。
